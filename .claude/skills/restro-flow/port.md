# Build › Port

An MVP built outside this repository (reservations, D101; song requests, D99) is rebuilt inside the platform. The MVP is a **working spec**: what it does carries over (stories, data, rules); how it looks never does, because every screen is redesigned under D105 and D123. Its code is read, never copied in.

Stages 1–4 run once per product; 5–7 once per feature set, foundation first. The **port inventory** is the single source of truth throughout: every row has an id, and every spec story, ticket and acceptance step names the rows it covers.

1. **Intake (lead + Martin).** The MVP's code goes into a read-only folder outside the repo, pinned at one recorded commit; agents treat it like `C:\Platform` (read, never edit, branch or commit). A "how to run it" note sits beside it. The MVP runs only on its own made-up data, never with a live venue's POS or live payment keys (CLAUDE.md rule 7). Martin settles who owns the area after the port: the MVP's developer contributes pull requests under CLAUDE.md, or only accepts the port (stage 7). Done when an agent can start the MVP from the note.
2. **Inventory (agent sessions, models by D58).** `research` writes `docs/deliverables/<date>-<product>-port-inventory.md` (D114), one row per item, ids `RV-<n>` for reservations, `SR-<n>` for song requests:
   - **From the code, by search:** every screen and route, button, message, data table and field, outside service, setting, timer or scheduled job, role and permission. Done when each list was produced by a search the inventory names, so a rerun gives the same list.
   - **From the running MVP:** `run` and the built-in browser walk every screen as each persona, with screenshots; each path becomes a user story ("As a <persona> I want <x>, so that <y>") with its tap count, the baseline for stage 5.
   - **Gap hunt:** a second session on a different model reads the MVP against the inventory and lists what is missing. Then Martin sends the inventory to the MVP's developer with one question: what is missing? Done when both answers are folded in.
3. **Map and verdict (lead; Fable where money or the data model is touched, D104).** Every row gets a verdict, **keep**, **rebuild differently** or **drop**, with a reason, set against `GLOSSARY.md`, the decisions and the nine rules. Every choice hidden in the code is sorted: **covered** (a D-number decides it; ours wins), **technical** (the lead decides from best practice and reports it) or **product** (goes to stage 4). `domain-modeling` names the new concepts; `codebase-design` places the seams on our model (venues, areas, tables, payments). Then the rows are cut into feature sets, each sized by `SKILL.md`'s size test. Done when no row is without a verdict and every row belongs to a feature set or is dropped.
4. **Grilling (decision log, `build.md` Feature step 1).**
   - **Round A, the MVP's developer:** `to-questionnaire` on why the MVP does what it does, for the product rows. Martin sends it; the lead never does (`upkeep.md` → Outside question).
   - **Round B, Martin:** `grill-with-docs` on the product rows only, each question carrying the MVP's answer as the recommended default, unless a decision or a rule speaks against it. Covered and technical rows are reported, never asked.
   Done when every product row has an answer in the log; the D-numbers and glossary terms are written from it.
5. **Design, per feature set.** Operational screens (the staff night list, the floor plan, the DJ page) get their screen plan in this window (`ship.md` §1, D123): stories from the inventory, patterns from `docs/guides/operational-screens.md`, a place on the admin map, a target tap count at or below the MVP's baseline. Guest surfaces get their entries in `docs/guides/menu-template-functionality.md` first, then `template.md`. `prototype` only for a direction question that needs a runnable answer.
6. **Build, per feature set.** `build.md` → Feature set steps 3–8. Each spec story lists the inventory rows it covers; a **keep** or **rebuild** row missing from every story blocks the spec.
7. **Parity and retire, per feature set.** `audit-behaviour.md` steps 3–5 walk every **keep** and **rebuild** row of the feature set in the new version. The MVP's developer confirms the behaviour matches; Martin accepts on a local preview. The rows are marked done in the inventory. After the last feature set, the inventory is closed and the MVP's developer archives the MVP; Restro deletes nothing of theirs.
