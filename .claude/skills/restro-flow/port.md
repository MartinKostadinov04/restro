# Build › Port

An MVP built outside this repository (reservations, D101; song requests, D99) is rebuilt inside the platform. The MVP is a **working spec**: what it does carries over (stories, data, rules); its looks stay behind, because every screen is redesigned under D105 and D123. Its code is read as a spec and rewritten here.

Stages 1–4 run once per product; 5–7 once per feature set, foundation first. Martin sees the plan card (`SKILL.md` §2) at stage 1, then once per feature set at stage 5. The **port inventory** is the single source of truth throughout: every row has an id, and every spec story, ticket, test and acceptance step names the rows it covers. The heavy zone and the model rungs apply at every stage (D104, `SKILL.md` §4).

1. **Intake (lead + Martin).**
   - The MVP's code goes into a read-only folder outside the repo, pinned at one recorded commit; agents treat it like `C:\Platform` (read only). A "how to run it" note sits beside it.
   - The MVP runs on made-up data and test keys only: its `.env` and real keys stay with its developer; the note names the keys it needs and Martin supplies test ones (`upkeep.md` → Human-only step). Never a live venue's POS or payment account (rule 7, D125).
   - Recorded once: whether the MVP holds real records (if so, moving them is a feature set of its own); every outside service and dependency it uses, each entering Restro only through a ticket that names it, with its terms checked (a service's commercial-use terms are a stop-and-ask for Martin).
   - Martin settles who owns the area after the port: the MVP's developer contributes pull requests under CLAUDE.md, or only confirms parity (stage 7).
   - After the pin, a change in the MVP reaches the port as new rows its developer sends; the pin moves only with Martin's OK.
   Done when an agent can start the MVP from the note and the tracker's prerequisites for the port are closed (today: T85, before the song-requests port).
2. **Inventory (agent sessions, models by D58).** `research` writes `docs/deliverables/<date>-<product>-port-inventory.md` (D114), one row per item, ids with a two-letter prefix per product (`RV-<n>` reservations, `SR-<n>` song requests):
   - **Things, from the code by search:** every screen and route, button, message, data table and field, outside service, setting, timer or scheduled job, role and permission. Done when each list names the search that produced it, so a rerun gives the same list.
   - **Rules and defaults, from the code:** every validation, default, limit, calculation, state transition, ordering rule, interval, retry and failure path, each with its file and line, and every value in data or config that drives behaviour (enum values, seed rows, email and message templates, database constraints). Done when every field, timer, service and status row names its rules or "none".
   - **Stories, from the running MVP:** `run` and the built-in browser walk every screen as each persona, with screenshots; each path becomes a user story ("As a <persona> I want <x>, so that <y>") with its tap count, the baseline for stage 5. Done when every screen and route in the code list was reached or is marked unreachable with the reason.
   - **Gap hunt:** a second session on a different model reads the MVP against the inventory and lists what is missing. Then Martin sends the inventory to the MVP's developer with one question: what is missing? Done when both answers are folded in.
3. **Map and verdict (lead).** Every row gets a verdict with a reason, set against `GLOSSARY.md`, the decisions and the nine rules: **keep** (the behaviour carries over as is), **rebuild differently** (the behaviour changes; looks change on every row and do not count) or **drop**. Each behaviour a decision adds that the MVP lacks gets its own **add (from D<n>)** row (D99's lock window and backers, D101's channels and deposits). Every rule row is sorted: **covered** (a D-number decides it; ours wins), **technical** (the lead decides from best practice and reports it) or **product** (stage 4). A drop or rebuild that no decision or rule forces is a scope choice, so it is a product row too (`SKILL.md` §3). **Keep or bug:** a row whose MVP behaviour breaks one of the nine rules, a decision, or an invariant of the risk plan (stage 5) is **rebuild**, never **keep**, and its stage 7 fixture leaves that behaviour out, so a bug in the MVP is never copied faithfully. A risk plan written later sends its rows back through this check. `domain-modeling` names the new concepts; `codebase-design` places the seams on our model (venues, areas, tables, payments). Then the rows are cut into feature sets, each sized by `SKILL.md`'s size test. Done when every row has a verdict and every kept, rebuilt or added row belongs to a feature set.
4. **Grilling (decision log, `build.md` Feature step 1).**
   - **Round A, the MVP's developer:** `to-questionnaire` on why the MVP does what it does, for the product rows. Martin sends it; the lead never does (`upkeep.md` → Outside question).
   - **Round B, Martin:** `grill-with-docs` on the product rows only, each question carrying the MVP's answer as the recommended default, unless a decision or a rule speaks against it. Covered and technical rows are reported, never asked.
   Done when every product row has an answer in the log; the D-numbers and glossary terms are written from it.
5. **Design, per feature set.** Operational screens (the staff night list, the floor plan, the DJ page) get their screen plan (`ship.md` §1, D123): stories from the inventory by row id, patterns from `docs/guides/operational-screens.md`, a place on the admin map, a target tap count at or below the MVP's baseline. The plan is kept in the inventory beside its rows until `to-tickets` copies it into the ticket. Guest surfaces get their entries in `docs/guides/menu-template-functionality.md`; whether a guest surface is a template is a stage 4 answer (for song requests, Q78), and a template follows `template.md`. `prototype` only for a direction question that needs a runnable answer.
   **Risk plan,** written by the planning session beside the screen plans and kept in the inventory:
   - **Robustness:** the feature set's hot spots (things at once, repeated, late or failing halfway: two guests booking the same table, two backers boosting at once, a hold captured twice, the service day closing mid-request, the DST change) and one invariant sentence per hot spot (`audit-robustness.md` steps 1–2).
   - **Security:** the threat model of what the feature set adds: its new entry points (a public booking page, a request page without a table), roles (the DJ), money and personal data (`audit-security.md` step 1).
   - **Journeys:** each path that crosses personas, written as one chain of story ids (a guest books, staff confirm, the email arrives, the guest is seated).
   The spec carries the invariants and the threats as acceptance criteria, so the build writes their tests first (`tdd`). Done when every operational screen of the feature set has its screen plan, every guest row its functionality entry, and every money, timer, status or entry-point row a hot spot or threat, or "none" with the reason.
6. **Build, per feature set.** `build.md` → Feature set steps 3–6. `to-spec` writes from files, not from the conversation: the inventory, the decision log and the D-numbers of stage 4; its user stories are the inventory's stories by id. The spec ends with "rows of this feature set: n, covered: n"; a keep, rebuild or add row missing from every story blocks the spec.
7. **Audits, parity and retire, per feature set.** First the two audits on the finished feature set, from its risk plan: `audit-robustness.md` steps 3–6 (one loop per invariant) and `audit-security.md` steps 2–8 (the threat model is stage 5's). A critical or high finding goes to Martin at once; every finding is fixed through `bug.md` before parity starts. Then each journey of the risk plan is walked end to end. A screen, button or message row is walked as `audit-behaviour.md` steps 3–5; every other row is proven by a named test, recorded beside the row in the inventory. For rule rows, the MVP's own outputs on a recorded input sequence are the test's fixture (a **golden master**: the queue order after a given sequence of requests, a reservation's status after each action). The MVP's developer confirms parity from the per-row screenshots and fixture results Martin sends; Martin accepts on a local preview. Done when every row of the feature set is marked done in the inventory. After the last feature set, the inventory is closed and the MVP's developer archives the MVP.
