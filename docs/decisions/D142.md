# D142: The event model — the minimal key set of what a night can be measured by, with no personal data anywhere in it

Ticket #335 (tracker T84). A night at a venue leaves service rows (orders, sent orders, payments, waiter calls, the Log), and those answer what happened. They do not answer how a night went: how many phones scanned, how many of them ordered, what was looked at and never ordered, how many payments were begun and abandoned. Reservations (#321, #323) and every later count of Martin's rest on those numbers, so the model goes in first and alone: the seam, not a report.

Three things decided this, in this order:

1. **One closed union of kinds.** The kinds live in `packages/core/src/events/kinds.ts` as a zod discriminated union of strict objects. A kind carries the fields that kind needs and nothing else; the union refuses anything it does not name. A later question of Martin's adds a kind to that file, with no migration: the database checks the *shape* of a kind (a lower-case name of dots and underscores), never the list.
2. **No personal data, anywhere.** There is no field and no column for a name, a phone number, an email address, an IP address, a device id, a user agent, a card digit, a position or any text a guest typed. A guest is only ever the table's sitting, and nothing links one sitting to another. The phone value the guest API uses elsewhere is not sent with an event and not asked for by its endpoint. A property test tries every personal field name we could think of, on every kind, with any value, and every one is refused; the table's columns are pinned by a test as well.
3. **An event goes in with the write it measures.** `recordEvents()` in `packages/core/src/events/record.ts` is the only writer of `guest_events` (rule 1, beside `core.apply()` for menu data and `applyService()` for service data), and the service engine offers it to every handler as `stx.recordEvents(...)`, inside that command's own transaction. So a line on the order and the event that counts it commit together or not at all, and the two can never disagree.

## The nine kinds

| Kind | Fields of its own | Recorded by |
|---|---|---|
| `menu.opened` | — | the phone (the guest API) |
| `item.opened` | our own node id | the phone (the guest API) |
| `language.chosen` | the locale | the phone (the guest API) |
| `order.line_added` | our own node id of the dish | the order write path, per dish an edit moved |
| `order.line_removed` | the same | the same |
| `order.send_attempted` | the outcome (`ok` or the refusal code) | the Send write path, on every path it can take |
| `pay.started` | the amount, once priced | the payment write path (on the bill, and pay-first) |
| `pay.finished` | the outcome, the amount captured | the write that settles the payment, once only |
| `waiter.call_opened` | — | the waiter-call write path, once per call, not per tap |

Every row also carries, NOT NULL: the tenant, the venue, the service day, the table, the moment, the kind, the retention class, and the provenance service data carries (source, actor, job; no layer — D122 §9). The sitting is on the row when there is one.

- **Only three kinds may be reported by a phone** (`menu.opened`, `item.opened`, `language.chosen`): the three things that happen wholly on the phone and leave no service row. Everything else is recorded by the write that decided it, so a tampered phone can never invent a conversion, a payment or a call. `POST /api/guest/events` refuses any other kind, and core's own union refuses it again.
- **The two order kinds carry the dish, and one edit can move several.** A line that was added and taken off again before a Send leaves no service row at all, so these two events are its only record; without the dish they would say that somebody changed their mind once, which measures nothing. A sent line is in the service rows, so look-then-buy is `item.opened` read against the order's own lines. The write path compares what is live dish by dish before and after an edit and records one event per dish that moved, so a restore of a whole order reads as the adds it was.
- **An outcome is a code of ours or `other`.** `order.send_attempted` and `pay.finished` need "it worked, or how it did not" without making the kind list open-ended, so they carry one short code. Anything that is not a code of ours becomes `other`: an event is never worth failing the write it measures.
- **An event never fails its write.** An amount that cannot be made (no price yet, a currency we do not take) is left out rather than thrown; a refused handler's event is kept past the savepoint where the refusal itself is the measurement (a Send that was tried and refused).
- **Money is integer minor units** through the `money` module (rule 8): `amount_minor` and `currency`, never a float.

## Retention

Two classes, the Log's own (D122 §9): `night` (31 days) and `record` (18 months). **Every kind is `record`.**

The Log's `night` class exists because those rows carry personal data, so holding them longer has a price. Here it is the other way round: these rows hold no personal data by construction — that is the whole design — so a longer retention costs nothing a guest could mind, and the rows are small. Against that stands what a question costs when the nights it needs are gone. The questions these numbers exist for are not written yet, and the nights a later one will want to compare against are the pilot's first ones. `night` would throw those away a month in, and a kind moves from `night` to `record` only, never back — a move that does not bring purged rows back. So the events are kept the full 18 months from the start.

The purge job sweeps `guest_events` by class and service day exactly as it sweeps `log_entries` — it reads the class off the row, so this decision needs nothing of it — and a venue's purge erases them with the rest of the venue's service data.

## What the name is

`order.line_added` / `order.line_removed`, not the ticket's `bag.line_added`: `GLOSSARY.md` names this the **order** and lists "bag" among the words to avoid (rule 5 of the reading list). The guest page may still *draw* a bag; the model says order.

## Out of scope here

Dashboards, reports and any screen; the questions Martin will ask of these numbers (they add kinds, not tables); the schema split (T85). Paying and calling a waiter have no guest screen yet, so their events are proven at the write path and by a test that every kind has a writer, not through a page.
