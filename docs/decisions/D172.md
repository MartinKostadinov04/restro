# D172: Staging runs on Coolify on Martin's own server; production's host stays open

Martin, 2026-11-25. Staging is hosted on Martin's own server (Synex), which runs **Coolify**, a self-hosted platform that builds this repository from its Docker Compose file and serves it over HTTPS through its own proxy. It replaces the Railway staging environment D43 and D103 planned, which was never created.

## Decided

- **Where:** Martin's server, in the EU (his answer, 11-25), so the EU-only position of D43 and D54 holds. The server also runs Martin's other projects and self-hosted tools; Restro has its own Coolify project and its own private network there, and publishes no port of its own: only the web app is reached, through Coolify's proxy.
- **Address:** for now the `https://….sslip.io` address Coolify generates for the web service (Martin, 11-25); later `https://restro.synexcloud.com`, a subdomain of a domain Martin already owns, as DNS only (no Cloudflare proxy, Martin 11-25). The current one is staging's address for sign-in, the Turnstile widget, the Stripe test endpoint (sandbox check 4) and the wallet domain registration (check 5, #117), so check 5 no longer waits for the Restro domain (T25). Moving from one to the other is a variable change and a redeploy, plus a new Turnstile host name, Stripe endpoint and wallet registration.
- **Build:** Coolify builds the images on the server from `main`, from the repository's Dockerfile and `docker-compose.staging.yml` (#375). No image registry. Martin's answer: memory on the server is not a concern.
- **Version:** Coolify v4, kept on its latest release.
- **What runs:** the web app, the worker and the simulated POS (`sim-pos`), each a container on the private network. The simulated POS is approved for staging (Martin, 11-25, answering `docs/runbooks/staging-deploy.md` §9); the worker refuses source kind `sim` in production, so the approval cannot reach production.
- **What does not change:** the database stays Supabase `restro-staging` in Ireland (D43, D54); migrations run only from the approved GitHub workflow (PR #199), never from a container or this PC; staging uses Stripe in test mode only (D125–D127); agents never deploy, and Martin clicks every deploy (CLAUDE.md).
- **Files on staging:** photos and published menus are kept on one Docker volume both containers share (`ASSET_STORE` and `PUBLISH_STORE` = `local`), so they survive a redeploy; no public bucket and no CDN domain on staging.

## Left open

**Production's host.** Martin, 11-25: "we still don't have production, leave that for later." Until he revisits it, D43's and D103's Railway line stands for production. The deploy configuration names no host Restro must keep, so production can reuse the same images on Railway, on Coolify or elsewhere; D103's portability work ("a container image for web and worker") is what makes that true.

## Why

Staging on Martin's own server costs nothing extra and gives him the HTTPS domain check 5 needs today. D103's rule that a move waits for a trigger (an incident on a service night, or the bill crossing about 100 a month) was written for production hosting; staging had not been created, so nothing moves.
