# D90: Restore re-links a POS venue's till venue if still free, else refused

Restore re-links a POS venue's till venue if still free, else refused. POS venue structure = our mapper (order) + dictionary (names) over a copy of the till's structure: reorder, rename, hide; no own sections (narrows D47); syncs touch only the till layer. Each menu has its own draft/published version; venue Live = live menu published; one shell and design per venue for all menus.

Consistency fixes for venues and menus (Martin 10-12, after a review of D84–D89 against older decisions). (1) Restoring a deleted POS venue re-links its till venue automatically if it is still free; if another venue took it, the restore is refused, naming that venue (fixes D76 vs D87). (2) A POS venue's structure is edited only as a mapper (our placements and order) and a dictionary (our names over the till's), both starting as a copy of the till's structure on the first sync; it can reorder, rename and hide, and does not create its own sections (narrows D47 for POS venues). A sync rewrites only the till layer, so nothing is re-applied after each sync; new till items land at the end of their category's section (D20), deleted ones leave after a full read (rule 6). Enrichment (sold out, own description and photo, tags) stays allowed (D89). (3) Several menus (D88): each menu has its own draft and published version; the venue is Live when its live menu is published; switching the live menu publishes it. One template (shell) and one design per venue, the same for all its menus; guest features also per venue
