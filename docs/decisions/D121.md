# D121: How the guest page talks to the platform: two endpoints, the table code in a header, polling, the guards on each request, and the location pass

> **Refined by D122 (10-21, the ordering check):** the location pass is signed by the server and bound to the table code's generation and the sitting. Seeing the bill and the order needs it. Request limits count per phone. An Unconfirmed sent order's state shows on every phone for 15 minutes.

Martin 10-20, ticket "How the guest page talks to the platform" (#40 of map #29) with the #40 session (Opus), an Opus second opinion and a research subagent (Sonnet). Decision log: `docs/deliverables/2026-10-20-guest-api-decision-log.md`. Sources, filed under D114: the technical design (`2026-10-20-guest-api-design.md`), its second opinion (`2026-10-20-guest-api-second-opinion.md`) and what ordering apps do on a weak signal (`2026-10-20-weak-signal-in-ordering-apps.md`). Built on D72, D102, D111, D112, D115, D116, D117, D118, D119 and D120, which stand. Martin settled what a guest sees; the technical design is the session's, checked by the second opinion, and the design file holds it in full. Nothing here is built yet (D79).

**Two addresses on the web app.** The guest page asks for its table's state and sends one action at a time:
- `GET /api/guest/state` answers with everything one table's phones may see, or "unchanged" with the version it already has.
- `POST /api/guest/actions` takes one guest command with its action id and answers with the result and the fresh state.
- Both are on the guest page's own address, behind Cloudflare. They use no cookie, refuse unknown fields and are never cached.
- The web app never calls the POS. Reading a table's POS bills, D111's knock and sending orders are worker jobs; the phone sees their outcome in the state.

**The table code finds the table.**
- The code travels in a request header, never in the address or a log, and is never stored with a bag, order or payment.
- The web checks its shape, then asks the database's one guest lookup function for the table's venue and tenant (A5-P6). That function is the one pinned exception in the RLS guard test (A6 G13); Martin agreed to it.
- Every action re-checks the code inside its own database transaction. A code the venue retired stops working at once and the phone says "This table code is no longer in use".

**What a phone may see.**
- The table's label and whether ordering is on, paused, or limited by D118's guards.
- The bag's lines, the "Removed · Undo" window, the earlier bags, and the payment countdowns, with no holder.
- The table's bill as the last **reading** shows it, with its age: rounds marked guest or staff, each line's name, quantity, total and whether it is paid. A line's name is the item's name in Restro; a POS row Restro can't match shows "Other item". On a POS venue every item comes from the POS, so this is rare (Martin).
- Never: other tables, who added, sent or paid anything, a phone's or a network's identity, waiter names, POS bill numbers or ids, internal names or cost prices (rule 3).
- **An order's progress shows only on the phone that sent it.** That phone sees "Sending…", "Added to your bill" or D116's "We couldn't send your order"; an Unconfirmed order's reference stays until the guest closes it. The other phones see the lines leave the bag and the round appear on the bill. Martin saw no need to show other phones orders that may not go through. This refines D117, where every phone showed "Sending…".

**How often a phone asks.**
- Every 2 seconds on the bag and bill screens, and every 10 seconds on the menu. While the table has an order on its way or a payment countdown, every phone asks every 2 seconds on any screen.
- Never while the page is hidden. Once the page shows again, it asks at once.
- There is no slow-down for an idle phone (Martin: keep it simple). The server's answer can slow every phone when Restro is under load.
- Failed requests are retried after 4, 8, 16 and then every 30 seconds.
- After about 10 seconds without an answer, the phone shows D120's paused screen. Send and Pay are blocked, never queued.

**Bag edits show at once.** Adding, changing, removing, undoing and restoring show on the phone straight away. If the server refuses one, the phone says why and puts the number back (Martin, as ordering apps do). Send and Pay never show success before the server answers (D72).

**Retries are safe.** Every action carries an id made when the guest taps. A repeat of the same id gets the first answer and never does the action twice. An action that arrives much later than it was tapped is refused, so a phone coming back from a lost signal can't send a stale Send.

**The guards ride on the request, added by the page, never by the template.**
- **Location** goes with each action that changes or sends on-the-bill items, at a venue with the check on. The server checks it in memory and drops it. It is never written, logged or sent to error reporting (D118).
- **The location pass** refines D118's "every on-the-bill order checks again". After a passed check, that phone's on-the-bill actions at that table need no new check for 2 hours (Martin). A different table needs a new check, and the pass never lasts past the service day. The phone holds the pass; Restro keeps no copy and no phone identity. The venue sets the time under "More" in "Ordering on the bill": **"Check location again after"**, 2 hours by default, from 30 minutes to 6 hours. Each on-the-bill order still records the consent text version (D119).
- **Paying and pay-first items are never located.** A guest who refuses can still add, change and pay pay-first items, call a waiter or ask one.
- **Turnstile** runs only at Send (D119). A missing or failed result refuses the Send. It fails open only when Cloudflare itself can't answer, and every such case is counted.
- **The cap and the pace limit** (D118) are checked at Send. The open-table rule uses the latest reading and the worker settles it.
- **D111's knock:** a bill action carries what the phone saw of the lines it acts on. The worker reads the POS and refuses with "Your bill changed" only when one of those lines changed or went; a friend's new round doesn't refuse it.

**The consent screen** replaces D119's text, which said "each time you order", no longer true with the pass. It is the shortest version that still holds everything the law needs (Martin):
> **[Venue] and Restro check your location so nobody outside can order onto your table's bill.** Never stored. You can stop anytime, or pay first or call a waiter. [Privacy]
> **[Allow]** [Not now]

It shows at the first change of an on-the-bill item, once per phone per service day (D119).

**Abuse limits.**
- Cloudflare's single free rate-limit rule guards the actions address per network, set generously, because a club's guests share one Wi-Fi address.
- The web limits how often one table code may ask for state.
- A table may make 60 bag changes a minute (Martin: 60 for now); above it the phones see "Slow down a moment". Every trip is written to the venue's Log (D120) and alerts the Restro team.
- D117's and D118's limits stand: 50 lines, quantity 50, 3 orders waiting, the cap and the pace limit.
- Pranks from outside with a real table code are accepted for the pilot and counted.

**The template's contract** (`packages/shell/src/services.ts`, D72) follows this:
- The service state becomes the table's state above.
- The guest commands gain the bag commands.
- Send names the bag lines it saw.
- A result gains a refusal code and the id of what it made.
- A bill round no longer carries an action id.
- The face still only draws. The page's guest client is the only code that talks to these addresses (A5-P10).
- The shell still reads only published files for the menu (rule 4). The bag, the bill, the orders and the payments are the page's service state, which the template is given beside the menu.

**For the build** (Martin agreed): new tables for the shared bag, orders and their attempts, and the table's reading, and later payments, with id kinds for each. All writes go through Restro's single write path (rule 1).
