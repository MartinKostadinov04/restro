# D105: Templates are designed by agents in the repo, from the menu functionality file

Martin 10-17. Lovable produced the first template (Editorial Market) and set the direction; designing every template outside the repo does not scale. The repo is the design studio: the agent gets the technical context and the list of what a template must let a guest do, and brings the UI and UX through a set of best practices and skills.

- **Who designs.** An agent session runs the `template-design` skill inside the repo. The Editorial Market delivery in `docs/design/faces/editorial-market/2026-10-11/` stays as the archived first direction and is never edited. A designer outside the repo is still possible; their delivery goes through the same review.
- **What a template must do comes first.** `docs/guides/menu-template-functionality.md` is the one list of what a guest can do in a menu. Each entry has a status: *supported* (the platform runs it), *drawn, platform parked* (templates draw it; guests see it once the platform supports it, D71), *decided, not in the contract yet*, *planned*. Every template draws every entry in the first two statuses unless its brief exempts one explicitly; an ambiguous case is a stop-and-ask. Entries in the last two statuses are not drawn. A template missing a required entry stays hidden (D69). Every flow that adds, changes or removes something a guest can do in the menu revises the file in the same change, and a guardrail test keeps the file in step with the shell's feature list. The designer guide keeps the *how*; the file keeps the *what*, with a pointer per entry.
- **How a template is made.** Inputs: an id, names and descriptions in Bulgarian and English, a three-line intent, two or three visual references. The skill asks Martin for material first; without it the lead proposes three directions as one-screen prototypes (`prototype`) and Martin picks one. Visual direction follows the vendored frontend-design reference under Restro's overrides (D106); the face contract and §7.5 of the designer guide win on every conflict. The agent writes `packages/faces/<id>` directly. The record of the design is a design-intent note and the screenshot matrix under `docs/design/faces/<id>/<date>/`, for agents and the lead; Martin is not asked to read screenshots.
- **Review.** The design session spawns a `template-review` subagent on a different model than its own, so the check is independent. The reviewer checks functionality coverage first, then the contract tests, the §7.5 rules, the pinned audit (D106) and Matt's code review against the brief, and returns one list: missing, inconsistent, wrong, extra fat. At most two rounds; a third means the brief was wrong, and the session stops and asks the lead. The design session registers the template hidden (the web app's dependency, manifest entry and loader, `hidden: true`) so the preview and the screenshot matrix can show it; on a clean pass the reviewer finishes the wiring (picture, the tests that name templates, the words), lists it, and the session opens the pull request (`ship.md`).
- **Acceptance.** Martin accepts every template himself by clicking through it on a local preview before it is merged.
- **Continuous improvement.** Every design session's report ends with the review findings that point at the skills or the workflow rather than at the template, each with a proposed change; the lead turns the ones Martin accepts into Upkeep tickets.
- **Open.** The DJ request queue (D99) has no face contract yet; its place in templates is settled when the song-request port (T82) reaches the contract (Q78). The first template is a dark club-night face (T87).
