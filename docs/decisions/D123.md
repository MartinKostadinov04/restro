# D123: Operational screens are designed before they are coded; what enters from Anthropic's design skills, where, and what stays out

Martin 10-21, through the lead. Sources: the lead's review and proposal `docs/deliverables/2026-10-21-design-skills-in-the-flow.md` and its independent Fable review `2026-10-21-design-skills-plan-review.md`, whose changes Martin approved as "v3".

**Martin's goals, in his words.** Operational screens: clean, logical, quick to learn, few taps, "something that feels right". Guest templates: client-facing, never the platform's look. The second is D105 as it stands and nothing here touches it.

## The flow (refines D107)

D107 set the right goals (plain words, undo, one primary action, taps per story) and a check after the fact; nothing in `build.md` or `ship.md` designed a screen before its code, so the implementer invented the states, the words and the path, and the audit found them later.

- **The screen plan.** A ticket that adds or changes an operational screen carries a screen plan (`ship.md` §1): its stories with today's taps and a target, its place on the admin map, the pattern for each job, the one primary action, the states, the strings in both languages. The planning session writes it in the grilling, never the implementer; Martin confirms the stories and any behaviour choice. A target tap count comes from how the POS front end or a comparable admin does the same job (D115) and is an acceptance criterion the story's spec or the behaviour audit counts.
- **The admin map** (`docs/guides/admin-map.md`): every screen, what for, reached how, in how many taps; the baseline a new screen is placed on. A ticket that adds, moves or renames a screen updates it in the same change.
- **The pattern list** (`docs/guides/operational-screens.md` → Patterns): which pattern does which job, so the same job looks the same everywhere; a job with no pattern is a question to the lead, never a new pattern in a ticket. The table wins over a Platform file's pattern: the Platform's mechanics are ported, not its pattern (refines CLAUDE.md's Platform reference rule for operational screens). The inventory behind it is `docs/deliverables/2026-10-21-admin-pattern-inventory.md`; the divergences it lists are `change.md` candidates for Martin to pick from.
- **A known defect from the floor:** today's admin controls run 28 to 32 px against the 44 px target floor; one ticket resizes the shared controls, and until then a review does not repeat the finding.
- **Two reads at review** (`ship.md` §3): the pinned Vercel rules read the code; the guide reads the screen. The behaviour audit reads the screen the same way (`audit-behaviour.md` step 4).
- **Martin's acceptance is the design loop:** the hand-off lists the screen plan's stories with their target taps, so he tries those and says which felt long.
