# D173: A cache of an outside system's own objects is written by one narrow writer beside the two write paths, and never through either of them

The lead, 11-25. Earlier that day the lead ruled on open question 2 of [#520](https://github.com/MartinKostadinov04/restro/issues/520) — which write path owns our song table — and Martin challenged the foundation of the ruling. He was right to: it was reasoned from the wording of rule 1 outward and carried no evidence. This decision is that question answered again from three things the ruling skipped: our own precedent, the real cost of a writer in `packages/core`, and how comparable software separates a third-party cache from its own domain writes. The answer survives; three things about it change, and one claim in the brief behind it was simply wrong (see *What changed*).

Spec: #520, feature sets 1 and 2 (#521 cuts the table, #522 fills it). Decision log: `docs/deliverables/2026-11-22-song-requests-decision-log.md`. Research behind it: `docs/deliverables/2026-11-22-song-request-metadata.md` and `docs/deliverables/2026-11-22-song-request-catalogue-probe.md`.

## Decided

**1. There are three kinds of data in this repository, not two.** Rule 1 names the menu side (`core.apply(changeSet)`) and the service side (`applyService(command)`). A third kind has been here since before either feature was built: **an outside system's own objects, cached verbatim** — nothing a venue or a guest authored, nothing an owner could correct, keyed by the outside system's own id, and authoritative nowhere but at that system. It obeys rule 1 exactly: one write path per kind of data, one entry point per table. It is simply neither of the two named paths. **This decision does not qualify rule 1. It names a kind rule 1 already covered.**

**2. Our song table is that kind,** and it is the same kind as the payment provider's notices — not a new one. It is platform-wide, it is keyed by the provider's own id, it carries no layer because there is no layer to carry, and the thing it exists for (a song request) is a separate write on a separate path.

**3. The writer.** One module, one exported entry point, in **`packages/core/src/service/`**, beside `notices.ts` — not a new folder under `packages/core/src` (see *The real cost of a writer*). It:

- runs on `withSystem`, platform-wide, with no tenant and no venue: the catalogue is one platform's, and so is the search's daily ration;
- is keyed by the provider's own id and inserts with `onConflictDoNothing`, so a repeat is a no-op and the search never has to ask first;
- carries `source`, `actor` and `job` through `serviceProvenance()` and `provenanceChecks()` (rule 2), and **no layer**;
- touches nothing `apply()` or `applyService()` owns: no `field_values`, no `events`, no resolved document, no snapshot, no service row;
- **takes every write to the table** — a song seen for the first time and a later refresh of the same row alike. Not only "remember" (see *How comparable software does it*).

**4. Only the music search may call it, and that is pinned rather than stated.** A dependency-cruiser rule in the shape of `notice-route-records-only` names the one folder that may import the module, so "no other caller" is a check and not a sentence in a ticket.

**5. The table joins the write-target guard.** `packages/core/src/write-targets.test.ts` is where rule 1 is actually enforced, per folder and per table name. The song table is added to `SERVICE_TABLES` and `SERVICE_WRITE_TARGETS` with a comment naming its ticket, exactly as `providerNotices` was added by #108. The guard only tightens (D67); nothing in it is loosened for this table.

**6. Expiry is the purge job's, never the writer's.** `CLAUDE.md`'s *Never* and D83 put every bulk erase in the purge job through `restro_purge`. A song row leaves the table the way a provider notice does: `purgeProviderNotices` in the daily purge tick, outside any organisation. The writer inserts and refreshes; it never deletes.

**7. The domain effect never comes out of the cache.** A song request is service data (#521, D122 §9): an `applyService` command writes it, carrying the song's id, and that command never writes a song row. Recording a song and asking for it are two writes on two paths — which is the same split as a provider notice (recorded by its own writer) and the payment reading made from it (`payment.observe`, an `applyService` command).

## Why

### Our own precedent, which should have been read first

Three narrow writers already sit beside the two write paths, and each says so in its own file:

- **`appendSourceRecords`**, `packages/core/src/apply/sources.ts` — the POS's raw payloads, cached verbatim and keyed by `(integration, external type, external id, content hash)`. Its header: "Rule 1 keeps writes to the document (nodes, values, links, placements, events) in apply(); these two tables are not the document". It is not an op of `apply()`; the worker's sync jobs call it directly.
- **`startJobRun` and its siblings**, `packages/core/src/apply/job-runs.ts` — header: "Not the menu document, so no apply()".
- **`recordProviderNotice`**, `packages/core/src/service/notices.ts` — a payment provider's own event objects. Platform-wide (`withSystem`, no tenant), keyed by the provider's event id with `onConflictDoNothing`, carrying service provenance and no layer, with its single caller pinned by the dependency-cruiser rule `notice-route-records-only`, and with every domain consequence deferred to a worker job that goes through `applyService`.

The pattern exists, so a second pattern for the same kind of data is exactly what rule 1 is there to prevent. The third one governs: it matches the song table on scope (platform-wide), on provenance shape (source / actor / job, no layer), on key (the outside system's id), and on consumer (service rows). The first two match only in being caches, and both are tenant-scoped.

**One correction.** The brief behind this decision suspected `packages/db/migrations/0016_venue_catalogue.sql` of already caching an outside catalogue. It does not. It adds two nullable columns — `catalogue_id` and `price_source` — to `barsy_venues`, the connector's venue link table, and backfills them. It records *which* catalogue a till venue sells from, as an integer, and holds none of the catalogue's contents. It is not a precedent for anything here.

### The real cost of a writer, and the one condition "narrow" depends on

A writer is not one size in this repository, and the 11-25 ruling asserted "narrow" without checking.

`applyService` is 57 lines on top of a 509-line engine, and every command pays for all of it: the command's schema and origin, a fresh sign-in for a settings change, `lock_timeout` 2 s and `statement_timeout` 5 s, the venue locked `FOR SHARE` and live, the table and its code, the permission read in the same transaction, `not_built`, the repeat check against the order row's ring of 64 action ids or the sent order's action id, the tap's age, the table's rate, the handler inside a savepoint with `keepOnRefusal`, a version bump on every table touched, the Log entry, the guest events, and a fresh table-state read after the commit. `apply()` is 2,278 lines: the tenant document lock, batched reads of nodes with their ancestors, links, field values, placements and cited source records, per-op validation against a field definition, identity resolution through `source_links`, value hashing, fractional sort keys, one `events` row per changed value, a revision step per touched node, and an applied / unchanged / rejected outcome per op.

None of it applies to a song row. There is no venue, no table, no actor, no permission, no layer, no revision, no Log entry and nothing to refuse — a song either was already known or has just been seen. Putting it through `apply()` would invent a layer and a provenance it has no business carrying; putting it through `applyService` would make it service data with an actor behind it. `recordProviderNotice` shows the honest size instead: about seventy lines, one Zod `strictObject`, one `withSystem` insert with `onConflictDoNothing`, two outcomes. So "narrow" is true.

**But it was true by luck, and the condition is now written down.** The guardrails are per folder, not per function. `db-write-only-from-core-write-paths` admits exactly `packages/core/src/apply/`, `packages/core/src/service/` and `packages/core/src/events/`, and the write-target guard pins table names against those folders. A writer in a new fourth folder would mean widening that dependency rule — and D67 makes a guardrail that only tightens, so that would be a stop-and-ask rather than a free choice. Inside `core/service/` the whole cost is one table name and one comment added to two lists. The module does not even need the write door: `notices.ts` writes through `withSystem` from `@restro/db`. That is why point 3 fixes the folder instead of leaving it to the implementer.

### How comparable software does it

The pattern has a name and two halves, and neither half routes the cache through the domain's own write path.

For the shape, it is the **anti-corruption layer** with a local projection of the outside system's reference data: a façade that translates the foreign model at the boundary and keeps it out of the domain's own objects. Microsoft's Azure Architecture Center credits Evans for it and warns that the layer is a thing to maintain and to monitor for consistency; AWS's Prescriptive Guidance describes the same pattern. The guidance that keeps recurring is to cache **stable reference data** at that boundary and to shape the façade around our own use cases rather than mirroring the foreign API one for one — which is the duplicate-collapsing #522 already owes a guest.

For the receiving half, it is the **store-then-process inbox**: verify, persist the outside object keyed by the provider's own id so that a repeat insert is a no-op, answer, and let a worker act on it afterwards. Stripe's own handler guidance expects an "already processing or processed" check against your own store; the broadly repeated implementation is a unique key on the event id with `ON CONFLICT DO NOTHING`, so deduplication happens in the storage layer rather than the application. That is `recordProviderNotice` line for line, which is a good sign: the repository arrived at the industry pattern before this decision noticed it had.

**And the research changed one thing about the writer.** The catalogue probe left open "the exact licence bucket of each field we would store, which is a read of its licence page rather than a probe". That page has now been read. The provider's API Services Developer Policies, section III.E.4, allow other Authorized Data to be stored "for no longer than 30 calendar days", after which an API client "must either delete or refresh the stored data" (III.E.4.c); Non-Authorized Data may be stored "but not longer than 30 calendar days" (III.E.4.d); and a client "must use reasonable efforts to ensure that their stored API Data is consistent with the current data" (III.E.4.e). So a table of this kind carries a refresh duty, not only an insert. That is why point 3 gives the one entry point every write to the table and not just the first sight of a song, and why point 6 sends the expiry to the purge job: the writer cannot own a bulk delete, and nothing else may.

What the policy does **not** settle is how long a song may be kept, because that depends on where the rows come from — the provider's search (#522 as written) or the open catalogue the probe measured, whose data is freely usable and under no such clock. That is D174's question, taken the same day, and not this one's.

## What changed from the ruling of 11-25

The answer stands: our song table gets its own narrow writer in `core`, one entry point, and only the search may call it. Four things are different, and whoever cuts #521 should read this file and not that comment.

1. **The reasoning is now the evidence, not the wording of rule 1.** Three writers of this kind already exist; the provider notices are the one the song table copies.
2. **Rule 1 is not qualified.** The 11-25 comment said "this qualifies rule 1". It does not: the third kind was always inside rule 1, and had merely never been written down. Nothing about the two named paths narrows or widens.
3. **The folder is fixed** at `packages/core/src/service/`, because the guardrails are per folder and a fourth one would mean widening a dependency rule against D67. The ruling left this open and called the result narrow anyway.
4. **The one entry point owns refreshes as well as first sights,** and the expiry belongs to the purge job through `restro_purge`. The ruling described a writer that only remembered.

## Not decided here

- **How long a song row may be kept, and how it is refreshed. Decided the same day, in D174:** a row is kept while something refers to it, is refreshed by its id before its thirty days are up, and is dropped by the purge job when the provider stops returning it. Release 1 keeps the provider's search, and the imported catalogue the probe argued for became its own ticket, #567. The research behind it is `docs/deliverables/2026-11-25-song-table-source-and-retention.md`. It was #522's blocker and never #521's, so nothing in this decision waited on it.
- **The table's columns, its id prefix and its migration.** #521's, under `packages/db/CLAUDE.md`.
- **Whether the search ever moves out of `apps/web`.** Ruling 1 of 11-25 on #520 stands: a server-side module behind a server action, moved to a package only when a second caller actually exists.
