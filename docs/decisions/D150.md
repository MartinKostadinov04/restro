# D150: No POS is connected without first being tested in a test environment

Martin, 11-18, asked about a POS vendor that offers no test installation, where the only way to try the connector would be a real club's live system. Decision log: `docs/deliverables/2026-11-18-pos-support-answers-decision-log.md`.

## Martin's decision

In his words: "We will connect no pos without prior testing in a testing environment".

- **This gates connecting a POS at all** — not just ordering and paying on it, and not just the write paths. Read-only menu sync is included.
- A vendor who cannot offer a test environment, a sandbox or a throwaway installation is not connected until one exists.
- It is the lead's reading that the gate is this wide: Martin's words set no narrower scope, and the narrower reading would leave a live club as the first test of a menu read.

## Why it matters beyond the obvious

CLAUDE.md rule 7 already forbids development and tests against a live venue's POS, and rule 9 makes staging config refuse production hosts. This decision closes the remaining way round them: deciding to connect a vendor at all, before any code exists, when the only system available is a real one.

## What this does not decide

- What counts as a test environment. A vendor's own sandbox, a local installation and our simulated POS are not equivalent, and nothing here ranks them. A connector built only against `sim-pos` has not been tested against that vendor.
- It says nothing about the pilot club's own system, which already has a connector plan.
