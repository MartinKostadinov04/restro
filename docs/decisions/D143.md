# D143: The database backup connects as its own read-only role, with BYPASSRLS

The worker's `db-backup` job (ticket #320) runs `pg_dump` as a dedicated login role, `restro_backup`: `SELECT` on every table and sequence of `restro` and of `drizzle` (the migration journal), `USAGE` on those two schemas, no `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` or `CREATE` anywhere, no access to the queue schema, sessions read-only by default, and the one `BYPASSRLS` among the roles Restro's code connects as. Refines D83 and D103.

**Why it needs the bypass.** Every tenant table has forced row-level security (`app.tenant_id`), so a role that is held to it sees no rows without a tenant set. A backup that cannot read every tenant's rows is not a backup. `pg_dump` sets `row_security = off`, so a role without the bypass makes it fail with an error rather than write an empty dump (a test proves it); the failure is loud, but it is still no backup.

**Why not the alternatives.** The migration owner can read everything, but an hourly job that holds the owner's credentials can also drop and change anything: worse than the loss it guards against. The app and purge roles are held to row-level security by design. Doing without `pg_dump` (the host's own backups) is priced in `docs/architecture/stack.md`; it does not give Restro a dump of its own.

**The never-list.** `CLAUDE.md` bars `BYPASSRLS` from app code. D83's purge role was the first approved exception to a never (a dedicated role for the one job that must cross tenants, with nothing but the privilege it needs); this is the second, on the same terms: a dedicated role, used by one job, read-only, created by `pnpm db:roles` from `packages/db/src/table-access.ts`, its connection string (`DATABASE_URL_BACKUP`) set only on the worker. No other code may use it, and no other role may have `BYPASSRLS`.

**How it is created and checked.** `pnpm db:roles` creates it where `DATABASE_BACKUP_PASSWORD` is set (without the password a missing role is not created and an existing one is only checked), and fails if any attribute or grant differs. A role with `BYPASSRLS` can be created only by an owner that holds it; CI's `migrations-hosted-owner` job replays the roles as an owner shaped like staging's (not superuser, `BYPASSRLS`), which is the proof that this works on the hosted database and not only on a local superuser.

**Not in the dump.** The queue schema `pgboss`: pg-boss creates tables there while it runs, which no grant made beforehand can cover, and what it holds (queued runs, schedules) is rebuilt when the worker starts. A new schema is a deliberate choice: a test fails until it is listed as dumped or as left out.
