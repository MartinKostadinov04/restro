## Goal
Settings gets a General section where an owner edits the organisation's name and its address name (the first part of every guest address, `/m/<organisation>/<venue>`), with the old name redirecting afterwards. A venue's own address row shows and edits the second part on the same form. Deleted venues shows when each venue will be erased and offers "Delete permanently" (owners, typed name), which erases it now.

## What the foundation already gives you (do not redo)
- The organisation's address name is Better Auth's `auth_organization.slug` (unique platform-wide, D84). Core: `organizationAddress(pool, tenantId)` reads it; `organizationSlugIsFree(pool, organizationId, slug)` says whether a new one may be taken (not another organisation's current or earlier name; the organisation's own earlier name may be taken back); `recordOrganizationSlug(pool, { organizationId, previousSlug })` remembers the old name after the change, so `o/<old>.json` redirects (`packages/core/src/apply/organization.ts`). `isOrganizationSlug` and `MAX_ORGANIZATION_SLUG_LENGTH` are in `@restro/core`.
- Renaming the organisation over HTTP is disabled (`DISABLED_HTTP_PATHS` in `apps/web/src/server/auth.ts`); a server action calls `getAuth().api.updateOrganization({ body: { organizationId, data: { name, slug } }, headers: await headers() })` directly (the precedent for a direct call: `setActiveOrganization` in `apps/web/src/server/actions.ts`). Keep the HTTP path disabled. `restro.tenants.name` was copied from the organisation at creation: update it in the same action with a small core writer `renameTenant(pool, tenantId, name)` you add to `apply/organization.ts` (the app role may UPDATE `tenants`).
- After an address change the worker rewrites the guest files; queue the jobs with `enqueueJob` (`apps/web/src/server/jobs.ts`): `JOB_NAMES.publishOrganizationIndex { tenantId }` (writes `o/<new>.json` and the redirect under the old name), and for every venue of the organisation that is not deleted `JOB_NAMES.publishTableTokens { tenantId, venueId, retired: [] }` (the table files carry the organisation's name) and, for each one with a live menu, `JOB_NAMES.publishFiles { tenantId, menuId, venueId }` (`venues.live_menu_id`). Failing to queue is not a failed save: answer `filesQueued: false` like `renameVenueSlugAction` does.
- A venue's address name: `renameVenueSlugAction` and `venue-address.tsx` exist (D84 rules: unique in the organisation, old names remembered, `taken`). Only the form changes: it shows `/m/<organisation>/` as a fixed prefix and the venue part as the field; the preview is `guestMenuPath({ organization, venue })` (`@restro/core`). `venue-settings.tsx` renders it: pass it the organisation's slug from `organizationAddress`.
- Deleted venues: `listArchivedVenues`, `deleted-venues-list.tsx` with Restore (its `till_taken` refusal is done), `purgeVenueAction({ venueId, confirmName })` → `{ ok: true, name, queued } | { ok: false, error: 'not_allowed' | 'invalid' | 'not_deleted' | 'name_mismatch' | 'failed' }` (`apps/web/src/server/venues-actions.ts`). The bin's length is `VENUE_BIN_DAYS` (`@restro/core`); the daily purge erases a venue once it is that old.
