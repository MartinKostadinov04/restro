# Lead workflow

For the lead agent: the session Martin talks to, which writes briefs, starts agents, reviews and merges. Coding agents working from a brief can skip this file.

- **Every new request starts with the `restro-flow` skill** (`.claude/skills/restro-flow/`): classify it; a Build, Change, Bug, Audit or Upkeep flow gets the plan card and waits for Martin's OK; Explain, Decide and Outside question are answered directly.
- **At most two agents running tests at once** (Martin 10-11): more load the one PC until tests time out. A read-only agent (`research`, a review sub-agent) does not count towards the two, but it still costs usage: cheapest model that can do the job (D58).
- **At most one finished build waits for Martin's acceptance** (Martin 10-17): the lead starts no second build until the first is accepted. The acceptance is the gate for a stage branch to reach `main`.
- **Cheap work goes to a cheap model, then gets checked** (Martin 10-17): a mechanical or exactly specified task goes to a Haiku or Sonnet session, and the lead reviews its diff; the lead does not type what a cheaper model can.
- **Never enter plan mode while agents run.** Plan mode freezes their edits too.
- **Model per task (D58):** Haiku for exact, mechanical tasks; Sonnet by default; Opus or Fable for complex work.
- **Model for planning (D104, D108):** Sonnet by default; Opus for a real trade-off or more than one area; Fable for the heavy zone. One rung at a time, the lead switches the session itself and says why in one line; the rung is sticky until the ticket's diff is reviewed. A higher model's proposal when Martin doesn't know. The steps are in restro-flow §4.
- **Code it or brief it:** the lead codes only what changes one of the nine rules, a migration or a guardrail; everything else, core included, goes to a session on the model the ticket names (Opus for `apply()`, resolver, snapshot, sync, RLS, money). The lead codes its three things on whatever model it runs (D108) and reviews every diff either way.
- **Tasks and tickets are GitHub issues from the moment they exist** (Martin 10-17): label `task` until the issue carries `ship.md`'s Restro block, then `ready-for-agent`. `docs/open-items.md` keeps one line per open issue with its number and owner; `docs/tracker.md` takes no new T entries (the open T-numbers stay until they close). `docs/agent-briefs/` holds the briefs written before 10-16.
- **Direct commits** (Martin 10-17): decisions, open items and agent docs the lead may commit straight to the stage branch; code and anything a guardrail tests goes through a pull request; docs that describe a feature land with its pull request, not before.
- **A pull request per ticket into the stage branch.** The ticket session opens it when its work is done; CI runs on every pull request and on pushes to `main` and the stage branches (`<stage>/foundation`). After review and a green CI, the lead merges the pull request into the stage branch. Locally run only typecheck and the tests of the merged areas. Merge conflicts are resolved on the task branch and its touched tests re-run, never on the stage branch directly.
- **Open questions and tasks:** `docs/open-items.md`, one line each by owner. Read it when planning, reporting status to Martin or picking the next work.
- **Recording a decision:** its own file `docs/decisions/D<n>.md` plus its row in `docs/decisions.md`, same commit (`docs/agents/domain.md` has the format and the numbering rules). **A question:** full text in `docs/tracker.md`, one line in `docs/open-items.md`, same commit. **A task:** a GitHub issue (above). A closed issue or answered question leaves `open-items.md`. Only Martin decides; agents propose in their reports.
- **Production deploys** never Thursday–Sunday 18:00–08:00 Europe/Sofia, except fixes Martin approves.
