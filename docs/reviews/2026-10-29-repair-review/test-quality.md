### (d) The payment-route property (`worker/payment-route.test.ts`, "the model" :1394-2069, RR-A2-1)

What the model asserts. Per night: two guests' payments on one table, 0-3 POS faults (14 kinds, :1397-1411), 0-1 provider fault (:1412-1420), up to 3 waiter or provider "happenings" (:1450-1480), a slip round, notice timing, late-landing length, lag, a manager who answers each unconfirmed close "as the till shows it" (:1894-1933). The oracle is the simulated POS (`till()` :1866-1885). Invariants (`invariants`, :1936-2069): every payment settles (:1961); a capture only after proof of a close (:1998-2002); no release after a close was attempted unless "No receipt" (:2004-2009); a hold never released while the till shows Restro's card payment on a closed bill unless a second "No receipt" (:2011-2016); the capture equals the card payment on the closed bill (:2018-2022); a closed bill is captured or the owners are told (:2023-2026); stranded and capture_failed alert (:2030-2036); refunds recorded; every notice handled; no line in two payments; one holder per payment table (:2051-2068). numRuns is 25 (:1542), no fixed seed; five `examples` pin earlier counterexamples (:1543-1655).

Is the invariant itself wrong? The two seeds in `flakes.md` RR-A2-1:

- Seed 1085069335 (closeBill `landsThenHangs`, capture `server_error`, hold `expired`, slip round, two payments): `expect(SETTLED).toContain(row.state)` (:1961) failed with state `unconfirmed`. Candidate verdict: production was wrong, the invariant was right. Evidence: commit `c41f412c` ("a capture that got a server error ... the provider keeps the server error under that key ... the payment stayed unconfirmed with nothing left to answer"), which adds exactly this seed as an example (:1631-1655) and a focused test (:1020-1118); `8f9a9053` names the reason (`hold_expired`/`not_held`). Both are before the pin.
- Seed -950485348 (no fault, provider `expired` before `payAndClose`, `lateLanding` 20 000): failed with state `closed` not in SETTLED. Candidate verdict: the invariant is right (a closed bill with a gone hold must end `capture_failed` and tell the owners), and I believe the same family of production hole as seed 1. But I could not verify that the pinned code fixes this seed: it is not among the five examples (:1543-1655), and the nearest focused test (:1093-1118) adds a `capture` server error that this seed did not have. That is RR-A11-6. A9 should replay `-950485348` at the pin.

Where the model is weak (none of these made the invariants wrong): no tips (so M5 is invisible), no pay-first rounds, only two payments, manager always answers (a payment that waits forever for a manager is not a violation by construction), 25 runs. `invariants` 4 reads the production Log, so a route that logged a claim wrongly and acted wrongly would agree with itself.

### (e) Playwright specs

`e2e/tables.spec.ts:392` ("an area is renamed and moved; a table is hidden ..."). Waits: `act()` (:73-84) sets `page.waitForResponse` before the trigger and then `page.waitForLoadState('networkidle')` (the discouraged wait); `expect.poll` for reorder (:425-440); `toast()` and `toBeVisible` auto-retry; `runWorker()` asks a long-lived helper (:131-170). No fixed `sleep`. The test is about 40 steps with five worker round trips in one test under Playwright's default 30 s test timeout (`playwright.config.ts` sets no `timeout`; only web-server timeouts at :132-154). The commit that last "fixed" it (`76833e4f`, #196) says "No assertion or timeout changed". The recorded errors (`page.waitForResponse: Target page ... has been closed`, `toBeHidden failed`) are what a 30 s timeout looks like from inside; that is the likelier cause than a race in one wait. A second candidate cause is the helper itself: `addressOf` (:104-117) retries the thumbnail click inside `toPass` while the first click's dialog may open late, then presses Escape once and expects hidden; two opens need two Escapes. State leak: serial mode on one shared `page` and `context` (:40-ish, `test.describe.configure({ mode: 'serial' })`), `seed` in `beforeAll` only; the `finally` restore (:462-471) renames the area back but cannot run if the page was closed by the timeout, which is what `seed` now repairs (#196). Counts in `8 маси, 6 с код` (:431, :453) depend on earlier tests having created codes: order dependent.

`e2e/guest-pay-return.spec.ts:33`. Waits: `toBeVisible()` on the face (:45), then reads `page.url()` synchronously (:48-52) and the collected request list (:55-58). The face is visible from server-rendered markup before hydration; the address is cleaned in a mount effect (RR-A2-2). So the assertion races the effect: the exact failure in `flakes.md` ("Received: ?lang=en&payment_intent=...") on the first try, green on retry. Two more things: the request list is read immediately, so late requests that would carry the secret may not exist yet and the check can pass vacuously (it only asserts `asked.length > 0`, :55); and it checks request URLs, not the `Referer` header, which is the leak RR-A2-2 names. State: `seed()` (:23-31, called by all three tests) reruns `seed-send-e2e.ts` against the shared fixture the Send specs use; browser storage is per context so nothing leaks between these three. The fix for the test is `await expect.poll(() => page.url())` or `toHaveURL`, not a retry.

## 6. Observations

- O1 `payment-refunds.test.ts:224-235` records a known limitation as expected behaviour ("pins the known limit"): a failed refund and a new one read together leave the failed row unmarked. If the limitation is later fixed, this test must be rewritten, and a reader may take it as a requirement.
- O2 `night-report.test.ts:104-117` renders a `capture_failed` line that `readNightPaymentsReport` never emits (night-payments.ts:1104). The renderer path is unreachable in production; the test does not say so.
- O3 `payment-table-race.test.ts` uses fixed sleeps of 300 and 500 ms (:107, :111, :136, :139). On a slow runner the test goes red for the wrong reason, never green for a wrong one. Not in `flakes.md`.
- O4 `alerts.test.ts` runs on the wall clock plus an offset and a "midday" time zone (:41-46, :73). The flaky "a pause" test (:525-566) asserts exact push counts across three clock regimes. I cannot judge the cause of the second push without running it.
- O5 The simulators are test doubles with their own tests (sim-pay x2, sim-pos x3). The worker property and the worker route tests trust them as oracle; the Stripe recordings are the only outside check, and they skip hold expiry and the guest-step case (two `it.todo`). - O6 `guest-api.test.ts` checks the no-store/no-referrer headers on 200, 401 and 404 answers only (:126, :138, :238, :434).
- O7 `payments-connection.test.ts:83-98` never asserts that a failure was logged, so "never logs the link" stays true if all logging is removed.
- O8 `pay-route.test.ts:643` bounds the 18-month retention from below only (`> 17 months`), so keeping a payment longer than promised is invisible.
- O9 `tonight/actions.test.ts:22`: `identifyAtSharedDevice` is `vi.fn()` returning undefined; the PIN branch (wrong PIN, `device_waiting`) is covered only by the browser lane (`tonight.spec.ts:214` for the wrong PIN).
- O10 `pay-first.ts:583` `pos_higher` looks unreachable behind `matchRound` (a bill line dearer than its round line is `not_the_round`); a dead guard, harmless, but it is the "never a higher total" rule in name only.
