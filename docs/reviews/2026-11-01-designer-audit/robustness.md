# Designer audit: robustness (B5, "races")

**Who:** B5. **Pin:** `st/foundation` at `7dccd3a4`. **Database:** `restro_da_races` (local, my own). **Local branch with the tests:** `da/b5-tests` in `E:/Restro/.claude/worktrees/da-races` (commits `228d3111`, `43a7b170`; never pushed). Test files: `packages/core/src/apply/design-races.test.ts` (18 loops) and `apps/web/src/server/design/races.test.ts` (5 loops).

**Covered:** `setDesign`, `setStyle`, `setStyleStatus` in `packages/core/src/apply/apply.ts` (revision, contrast and logo checks, name rule, events); the tenant document lock and the venue row locks; `publishMenu` (lock order, what it reads, `serveVenueAgain`, the previous snapshot); `readDesign`, `readDesignRecord`, `hasInvalidDesign`; the snapshot schema's `design` block; `apps/web/src/server/design/{actions,service,styles}.ts`; migration 0047's unique live name and `removed_at`.

**Result in one line:** the write path itself is sound (one writer wins, no half-merge, names and Undo hold, one event per write); the trouble is at its edges: a lock upgrade that deadlocks with a publish, and a snapshot schema that breaks every stored snapshot when the contract changes.

## Hot spots: invariant, loop, verdict

| # | Invariant | Loop | Verdict |
|---|---|---|---|
| 1 | Of many saves from one revision, exactly one wins, the rest get `stale_revision` with the stored design, and the stored design is the winner's whole design (no field of a loser). | Eight concurrent `setDesign` calls with designs that differ on five pages, five rounds; plus three at once from revision 0. Checks one winner, `storedDesign.revision`, deep equality with the winner's input, one event per revision. | Holds. Went red under M1 (revision check removed) and M8 (document lock made a no-op). |

Red under M5 and M6 (checks removed). The loop proves the checks, not a race window: there is none, because every `apply` for a tenant is serialised. |

Mutations used (each applied, run, reverted with `git checkout`; nothing of product code is left changed): M1 `if (op.expectedRevision !== current.stored.revision)` to `if (false)`; M2 `styleNameKey` without the lower-casing; M3 the name check on restore in `setStyleStatus` to `if (false)`; M4 `styleEvent` writing its event twice; M5 the contrast refusal to `if (false)`; M6 the logo check to `false`; M7 `readDesignRecord` using `parse`; M8 `lockTenantDocument` made a `select 1`; M9 the snapshot theme built from a default design. The web loop for My styles went red with `SavedStyleContentSchema.parse` instead of `safeParse`.

Fix proposals (for the lead, not made): DA-B5-1 parse the snapshot's `design` block leniently as the record does (fill missing options with Basic's, drop unknown ones, keep a value off the list as Basic's), and have `publishMenu` treat an unreadable previous snapshot as "none"; DA-B5-2 take the target venue's row `for no key update` in the first locking pass (not after a share lock), or have `publishMenu` lock its venue `update` first; DA-B5-3 compare against the stored record, not the displayed one (an invalid record is never "unchanged"); DA-B5-4 generate the Style id on the server, or refuse an id that is not the organisation's own with `not_found`.

## Observations

| Id | Point |
|---|---|
| O-B5-1 | Every `apply` takes the tenant document lock, so the design and Style races are serialised before the revision and name checks run. The row lock `for no key update` on the venue is therefore redundant against other `apply` calls; its only effect found is DA-B5-2. |
| O-B5-2 | `packages/core/src/apply/test-database.ts` `cleanUp` does not list `design_styles` (an FK to `tenants`, `restrict`). A test that leaves a Style behind makes the tenant delete fail; my tests delete theirs first. |
| O-B5-3 | The app's name key is coarser than the database's unique index (case-folded, trimmed, `bg-BG`), and JavaScript's `trim` is wider than `btrim`: a name never reaches the index in a form the app allowed but the index refuses. No database error was reachable through names. |
| O-B5-4 | Archiving, unpublishing and restoring a venue at once with a design save gave no database error in a four-round probe; I did not keep that loop (no mutation run against it). |
| O-B5-5 | The shared timing: a publish and a save overlapping depends on the publish's build time; on a quiet PC the window was wide enough to hit 6 of 6. |
