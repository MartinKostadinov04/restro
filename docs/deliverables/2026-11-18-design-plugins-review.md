# Switch off both plugins, lift five lines, add one screens flow

**Summary.** Neither Anthropic plugin should stay active inside Restro. Both are inert text with no scripts, hooks or downloads, but both reach Restro sessions through the Claude Desktop sync and can fire on Martin's own phrases ("what do you think of this screen?", "make this screen nicer"). That is exactly what decisions D106 and D123 keep out, and D123 records that both plugins were installed by mistake on 10-21 and removed the same day. The 11-18 reinstall changed nothing in content: the `frontend-design` text (v1.1.1) is byte-identical to the copy Restro vendored on 10-17, and the `design` plugin (v1.2.0) is identical to what D123 read. So D123 stands. The recommended step is to switch both off for the Restro project only, in a committed `.claude/settings.json`, and leave the decision to uninstall them elsewhere to Martin. Of the plugin text, only about five items are new and worth bringing into Restro's own files: a list of "AI tells" for reviewing guest templates, and a few small copy and layout lines. All of it belongs to guest templates or to review wording. None of it may touch the owner and staff screens, the Tonight screen, or the guest service screens (bag, bill, call a waiter, pay, receipt). The new "review the screens, record issues, fix them, verify" part should be one short flow file, `.claude/skills/restro-flow/audit-screens.md`. It reuses every check Restro already has by path and adds only what is missing: one severity scale, one finding format, a closing re-check by someone other than the fixer, a rule that turns repeated findings into tests, a stable label, and a cadence.

## Both plugins are live in Restro sessions, but only as steering text

**Facts, frontend-design.** The plugin is one skill, a README, a licence and a manifest: no hooks, no servers, no scripts, nothing fetched. The text was rewritten twice in 2026 (June and September), so an auto-updating synced copy can drift from what Restro reviewed.

**Facts, design plugin.** Seven skills (accessibility-review, design-critique, design-handoff, design-system, research-synthesis, user-research, ux-copy). The installed copy matches the version Restro read at commit bc8f6922, and upstream has not touched the folder since ([GitHub compare](https://api.github.com/repos/anthropics/knowledge-work-plugins/compare/bc8f6922...main)). It also registers seven connector servers (Slack, Figma, Linear, Asana, Atlassian, Notion, Intercom); this session already lists them as waiting for sign-in. The trigger phrases include "what do you think of this screen?", "review this design", "is this accessible?" and "what should this button say?".

**Inference.** The risk is behavioural, not technical. An agent that loads the un-overridden frontend-design text is told to take "aesthetic risk", open with a hero, pick a hex palette and typefaces, and "confirm with the client", which here means asking Martin. On an owner screen, which D107 wants calm and plain, that produces motion, flourishes and questions nobody wants, and no guardrail test would catch it. I could not test how often the model actually loads either skill unprompted; that is a likelihood, not a measurement.

## Keep the plugins out of Restro with one settings line each

**Facts.** A project can turn a plugin off for everyone who opens the repo. `enabledPlugins` is keyed `name@marketplace`, merges key by key, and a project value beats a user value; for a synced plugin the key is `"<name>@synced"`, and the docs name the committed `.claude/settings.json` as the way "to keep the plugin out of a project in every environment" ([Plugin loading reference](https://code.claude.com/docs/en/plugins/loading.md); [Settings reference](https://code.claude.com/docs/en/settings-reference)). A single skill inside a plugin cannot be turned off from settings: `skillOverrides` "doesn't apply to plugin skills" ([Skills docs](https://code.claude.com/docs/en/skills.md)). Restro today has no committed `.claude/settings.json` (the folder holds `launch.json`, `settings.local.json`, `skills`, `worktrees`) and no `enabledPlugins` entry. The setting `syncClaudeAiPlugins: false` turns off all synced plugins, including ones Restro may want (stripe is one), and a `false` in the shared file is ignored, so it is not the right tool.

**Inference.** Recommended: a committed `.claude/settings.json` containing `enabledPlugins` with `frontend-design@synced` and `design@synced` both `false`. Both plugins' useful text is already in the repo, so nothing is lost. The exact ids must be confirmed with `claude plugin list` before writing, and the effect must be checked in a fresh session, because the docs describe terminal and Cowork sessions and say nothing about Desktop worktree sessions (Restro uses `.claude/worktrees`). A fallback deny rule `Skill(frontend-design:frontend-design)` is plausible but untested for plugin skills. This is a small config change, not a CLAUDE.md edit, but Martin should still say yes. Anyone who actually wants either plugin for another project keeps it at user level; the project line only hides it here.

## The industry loop agrees with Restro's shape, with limits on what an AI reviewer can do

**Facts, review.** The standard methods are heuristic evaluation (scoped to one task or section, about 1 to 2 hours, findings one per row with the named heuristic) and cognitive walkthrough, which suits unfamiliar walk-up flows ([NN/g heuristic evaluation](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/); [NN/g cognitive walkthroughs](https://www.nngroup.com/articles/cognitive-walkthroughs/)). For accessibility, [WCAG-EM](https://www.w3.org/TR/WCAG-EM/) requires a defined scope, a sample, and at least one example per failed criterion; automated scans catch only some problems, and the UK government's service manual requires manual checks plus assistive-technology testing ([GOV.UK](https://www.gov.uk/service-manual/helping-people-to-use-your-service/testing-for-accessibility)). axe reports `violations`, `incomplete` (needs a human) and `passes`, with a selector per finding ([Deque](https://www.deque.com/axe/core-documentation/api-documentation/)), and Playwright recommends recording known issues as rule id plus selectors ([Playwright](https://playwright.dev/docs/accessibility-testing)). Visual baselines are committed and reviewed in the pull request ([Playwright snapshots](https://playwright.dev/docs/test-snapshots)).

**Facts, AI as reviewer.** The evidence is older-model and mixed. In an academic study, GPT-4 found 73 to 77% of a merged issue set against about 17 to 18% for one expert, but produced many false positives from misreading the interface and caught only 43 to 50% of problems that span several screens versus 83 to 86% for experts ([arXiv 2507.02306](https://arxiv.org/html/2507.02306v1)). A secondary report of a Baymard test of ChatGPT-4 on 12 screenshots found 24% of known problems and 9% of recommendations harmful ([Jakob Nielsen, opinion](https://jakobnielsenphd.substack.com/p/ai-ux-evaluation)); no 2026 study on current models was found.

**Inference.** Use the agent as a generator of candidate findings and rely on deterministic evidence where possible: selector-backed scans, computed styles, touch-target size, overflow at 320 to 390 px, console errors, screenshot diffs. Every finding must carry route, viewport, theme, selector or screenshot and a named check; a finding whose selector does not resolve is rejected; the reviewer must say what it could not see. Real-device feel (one-handed reach, glare in a dark club, a real screen reader, perceived polish, cross-screen flow, "is this the right priority") stays with Martin, as `template.md` already does with its phone checklist. Severity from a single rater is unreliable ([NN/g](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)), so the agent proposes and the lead or Martin confirms the top levels. Adding axe to the end-to-end suite would need a dependency, so it is a stop-and-ask under CLAUDE.md, listed below.

## The new part: five steps, three new rules, five one-line edits

**Shape (Inference, built from the notes).** One new file, `.claude/skills/restro-flow/audit-screens.md`, run by the lead through restro-flow and shown to Martin on the plan card first.

1. *Scope.* A round is one flow or a handful of screens, not the whole product, taken from `docs/guides/admin-map.md` and the guest Styles list. The batch size is my judgement; no source gives one. Record the commit reviewed.
2. *Review.* Machine checks first (the CI sweeps, the touch-target spec, and axe if approved), then the agent's walk calling `audit-behaviour.md` steps 3 to 5 unchanged: the eleven answers, Accessibility, `break-ui` (never for the guest persona), copy-rules, and for guests the Style review. Each finding is tagged with the check or D-number it breaks.
3. *Record.* One ledger file per round at `docs/reviews/<date>-screens-<area>.md` (the place `audit-behaviour.md` already uses), reusing the audit ledger's status flow. Fields: id, screen and route, persona, viewport and theme, steps, expected, saw, check or criterion, evidence, severity, effort, surface (guest or staff). The dedupe key is route plus selector plus criterion, and the agent searches existing issues before filing.
4. *Fix.* Reuse `change.md` step 4, which already turns a feedback list into one ticket per independent item, bundled by area as the designer-audit tickets were. Severity Blocking or Before the pilot is filed as bundle tickets with the `## Restro` block; Polish goes into one table issue for Martin to pick from, as in #349. Where the fix changes how a screen looks or works, Martin's go-ahead comes first (the 11-06 rule, and CLAUDE.md "stop and ask" for unspecified UX).
5. *Verify.* A session that did not write the fix re-walks the finding's own steps on the same viewport and attaches an after screenshot; the ledger row moves to `re-verified`. This echoes Restro's own "whoever judges a fix didn't build it" and the design-QA practice of re-checking on staging and then on the live site ([HubSpot](https://product.hubspot.com/blog/avoid-design-debt-with-better-design-qa)).

**Three new rules, defined once.** First, a severity scale in three words Martin has already read: *Blocking* (breaks ordering, paying or a staff core task, or an accessibility failure rated serious or critical by the scan), *Before the pilot*, and *Polish*; mapping to critical/high/medium/low is needed only if the audit ledgers and screen ledgers are ever mixed. The agent proposes, the lead confirms Blocking. Second, a regression rule: every finding that breaks a rule (touch target, overflow, wording in both languages, a contrast failure) gets a check in the existing home (`touch-targets.spec.ts`, the design sweeps, the copy rules) in its fix ticket, not only findings that are "Broken"; guardrails only tighten (D67). Third, a stable label, for example `screen-review`, documented once in `docs/agents/triage-labels.md`, instead of a new one-off label each wave.

**One-line edits elsewhere (Inference; none made).** A row for the new flow in the classification table of `.claude/skills/restro-flow/SKILL.md` §1 (edit on the `or/foundation` copy, which already differs); a hand-off line in `audit-behaviour.md` step 6; a sentence in `change.md` step 4 saying screen findings arrive as a feedback list; the label in `docs/agents/triage-labels.md`; and a row in `docs/deliverables.md` if the report is also a deliverable. Because the `restro-flow` files are lead-owned skills, these go through an Upkeep ticket under `writing-for-agents`.

**Cadence (Inference; no source gives one).** A round after each stage branch that changes screens reaches `main`, one before the pilot (the designer audit's own item 15 asks for a check before the pilot), and on Martin's call. The 11-10 agent pass over `or/foundation` (#387) is the natural first round, and it should be run before Martin's own single walk so that he walks a short list rather than a blank screen, as #387 says.

## Conclusion

The plugins add little because Restro did the hard part on 10-21: it read them, kept the parts that survive its two-surface rule and wrote them into files it controls, with overrides. What the 11-18 reinstall really exposes is a gap in how Restro keeps outside text out: D123 prevented a mistaken install by decision, but nothing stopped the sync from bringing the plugins back. A one-line project setting closes that, and a one-line mention in D123 should say it exists.

The larger finding is that Restro's missing piece is not a design skill but a loop: it has checks for every surface and no scale, no finding format, no closing re-check and no rhythm. Industry practice and Restro's own past waves (the designer-audit ledger, the walk-through tables, the catch-all issue Martin picks from) already agree on the shape, so the new flow is mostly writing down what the November walks did, with one honest limit built in: an AI reviewer proposes, deterministic checks and Martin's phone decide.
