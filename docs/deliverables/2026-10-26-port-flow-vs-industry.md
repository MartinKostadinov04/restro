## Findings, most important first

**1. Should fix, stage 1: who owns the MVP's code is never asked.** Every due-diligence checklist starts here. **[fact]** Under Bulgarian copyright law a commissioned work's copyright stays with the author unless the contract says otherwise; the commissioner gets a right of use, and the Supreme Court of Cassation (Decision 214/2016) held that such an agreement needs no written form, so an oral deal may exist and prove nothing (secondary sources below; the statute itself was not fetched). "Read as a spec and rewritten" lowers but does not remove the question, because rule rows copy behaviour with file and line and golden masters copy outputs. Also unasked: the licences of the MVP's own dependencies (a copyleft one is the classic finding) and keys that sit in the MVP's git history, not only in `.env`. *Add to stage 1:* "Martin records who owns the MVP's code and holds a written assignment or licence to Restro before any agent reads it (a human-only step; a plain rule, so no lawyer unless it is disputed, Martin 10-18). The folder holds the working tree at the pinned commit, not `.git`; the developer rotates any key that was ever committed. The MVP's dependency licences are listed in the inventory; a copyleft licence is a stop-and-ask."

**2. Should fix, stages 1 and 7: real personal data has one line, and "archive" undoes it.** Reservation records are guests' names, phones and emails. **[fact]** GDPR Art. 28(3) ends a processing with deletion or return at the controller's choice; stage 7 instead has the developer "archive the MVP", which for a tool that held real bookings keeps a copy of guest data in a private person's hands with no retention reason. Practice: identify the data, decide keep or erase, and get evidence of erasure. *Change stage 1:* "whether the MVP holds real records; if so, Martin decides at intake, per table, migrate or erase, and the hosted instance stops taking input when the pin is set." *Change stage 7's last sentence:* "the developer archives the MVP's code; its real records are migrated or erased as stage 1 decided, with the erasure confirmed in the inventory."

**3. Should fix, stage 7: no cut-over line for a live MVP.** The legacy patterns (strangler fig, parallel run, dual-write) are rightly absent: nothing runs with users, so a stop-the-world rewrite is the cheap and correct choice. **[fact]** Fowler's list has "Stop the World cutover" as a named pattern, used when the system is small enough. But a demo that a club has used has a public URL, a QR on a screen, maybe a provider account with holds. *Add to stage 7:* "If the MVP is reachable anywhere, the last feature set carries the cut-over: the MVP stops taking input, open holds or bookings are settled, its public links point to Restro, and only then is it archived." If nothing is live, the line costs one word: "n/a".

**4. Should fix, stage 2: the author never shows the system.** Practice everywhere, from acqui-hire onboarding to Fagan's reader role, is that the person who knows the system walks others through it; tacit knowledge ("that button exists because the bar ran out of change") does not survive a questionnaire, and this one is also asynchronous and filtered through Martin. **[fact]** The flow's only contact with the developer is a written "what is missing?" and Round A's questionnaire. *Add to stage 2, Stories:* "Before the agents' walk, the developer demos the MVP to Martin once, persona by persona, screen-recorded or noted; the recording is an input to the stories and to the gap hunt." Martin need not read code to watch a demo and ask "why", and the demo also catches "nobody used that", which practice calls the cheapest drop.

**5. Should fix, stage 3: the second-system effect lives in the "add" rows, and nothing brakes it.** Spolsky's and Brooks' warnings point opposite ways here, and the dangerous one is Brooks: the first system is small, the second carries everything deferred. **[fact]** D99 adds a lock window, backers, holds and captures; D101 adds channels, deposits, SMS; the MVPs have none. The size test cuts feature sets but never asks whether an add row is for the pilot. Martin has said never to design around a scope cut he has not made, so the question goes to him, not to the lead. *Add to stage 3:* "Each add row carries 'pilot: yes | later', a product row for stage 4; later rows stay in the inventory and leave the feature sets."

**6. Nice to have, stage 7: say when the golden master is recorded and where it lives.** Approval testing's point is that the recording is taken once, approved by a human, then frozen. port.md names the fixture but not its moment: if it is recorded late, the MVP may already have moved (the pin moves only with Martin's OK, so the risk is small), and if it lives only beside the MVP, parity depends on the MVP still running. *Add:* "recorded in stage 2 from the pinned MVP and kept with the inventory, so parity never needs the MVP to run."

**7. Nice to have, stage 4, Round A: ask what was removed.** Requirements recovery's known blind spot is negative requirements: things tried and taken out. One question in the questionnaire, "what did you build and remove, and why", recovers them for the price of a line.

**8. Nice to have, stage 3: a go/no-go.** Practice puts a decision after due diligence. If the map shows adds dominating keeps, the "port" is a build with the MVP as a reference and `build.md` → Feature set is the cheaper flow; the stage 5 card should say the keep/rebuild/add counts so Martin can see which it is.

## Where it could be lighter

Stage 7 asks every row for a named test and a golden master for rule rows. Scope the golden master to rows where the MVP *computes* something (queue order, totals, a status after an action); a validation or default row is proven by the ordinary Zod or unit test. State that a feature set whose risk plan is all "none" skips the two audits (today the text implies they always run). Keep the second-model gap hunt: it is read-only and the cheapest cross-check in the flow. Everything in stage 2 is mechanical and cheap on a small model. The flow is heavier than practice would spend on two demos but each heavy step buys something the nine rules or money needs; the savings above are the ones that lose nothing.

## Parallel reviewers and a consolidating lead

Martin's idea: several agents review the same layer or feature set at once, each reporting to one consolidating lead who also runs the operation.

**What practice says.** **[fact]** Fagan's inspection (IBM, 1976) is exactly this shape: several inspectors, a moderator who runs the meeting and a reader who paces it; secondary sources report 60–90 % of defects found before test. **[fact]** Perspective-based reading (Basili et al., 1996) gives each reader one role, tester, developer or user, and found the benefit comes from low overlap between what the perspectives find; in the replication, where two perspectives found the same defects, PBR lost its edge over a checklist. **[fact]** Course material attributes to Rigby and Bird (2013) that two reviewers find most defects and more add little (secondary; the paper itself was not fetched); Porter et al. found reviewer expertise mattered more than process. Delphi collects independent anonymous opinions first and synthesises after, to avoid anchoring on the first voice. Red/blue teaming adds an adversarial stance, which `audit-security.md` already has.

**What is known about AI reviewers.** **[fact]** Kim, Garg, Peng and Garg, "Correlated Errors in Large Language Models" (2025), over 350 models: when two models are both wrong they agree about 60 % of the time; larger and more accurate models are *more* correlated, even across providers; a 2026 multi-agent study found agents on the same backbone succeed or fail together, and chain or debate topologies couple them more than independent sampling; voting and ensembling assume an independence that LLM pipelines rarely have. Opinion: for Restro this means three agents of one vendor are not three independent opinions; they are one opinion read three times with different noise. Independence comes from different *inputs and perspectives* (the code vs the running app vs the decisions), from a different *kind* of oracle (a test, the golden master, Martin's taps), and only weakly from a different model rung. Consolidation bias is the other known failure: a lead that reads findings before forming its own view anchors on them, and one that filters silently loses the dissent that was the point.

**How to split.** Not by layer: three reviewers on the database, the server logic and the UI each bring the same perspective and none sees the cross-layer bug, which is where the journeys of stage 5 live. By perspective, one per reviewer, as the `audit-*` files already define them: rules and decisions (does it break the nine rules or a D-number), robustness (things at once, late, halfway), security (tenancy, roles, inputs, money), user flow (the journeys and the screen plan). Mix model rungs where the heavy zone allows (D104 sets the floor, not the ceiling). Three or four reviewers; past that, duplication grows and consolidation cost grows faster than findings.

**What the consolidator must do.** **[fact]** `ship.md` §3 already states the rule: "a finding is a hypothesis until checked in the code." So: de-duplicate; check each finding against the code, running one reproducing test where needed; keep every finding that reviewers disagreed on visible in the report with both views; rank by severity (the `audit-security.md` scale); write its own view only after the reviewers' reports are in (Delphi order); and list dropped findings with the reason, so a drop can be audited. It must never consolidate a review of code it wrote itself, and the lead's `code-review` on the pull request stays with the lead, outside the session that coded (`ship.md` §3).

**Cost and fit.** **[fact]** Restro already runs reviewers in pairs: two whole-branch reviews in `build.md` Feature set step 6, the Fable pre-publish check (`SKILL.md` §4), `template-review` on a different model (D105), the second-model gap hunt in port.md stage 2, and the lead's two reads of an admin diff (`ship.md` §3). **[fact]** `docs/agents/lead.md` caps test-running agents at two but exempts read-only ones; `/code-review ultra` is a billed cloud multi-agent review only Martin starts. So the idea is already half in place and the marginal step is small: make the reviewers read-only and test-free (they read the diff, the inventory, the decisions and the risk plan, and return hypotheses with file and line); only the consolidator runs tests, one at a time. That keeps the PC free and the parallelism costs tokens only.

**Where it fits in port.md.** Stage 7 is the natural place; stages 2 and 3 already have their cross-check or are Martin's. *Proposed wording for stage 7, replacing its first sentence:* "The two audits and the journey walk run as three parallel read-only sessions, one perspective each (robustness, security, journeys), on different model rungs where D104 allows; each returns findings as hypotheses with file and line and runs no tests. The lead consolidates: de-duplicates, checks each finding in the code, keeps disagreements and dropped findings in the report with the reason, ranks by severity, and then writes the loops (`audit-robustness.md` steps 3–6, `audit-security.md` steps 2–8) for the confirmed ones, one session at a time. A critical or high finding goes to Martin at once." For reviews generally: not on every pull request (cost); for a feature set's whole-branch review (`build.md` step 6) the same three-perspective pattern with the lead consolidating is a one-line change and worth it in the heavy zone.
