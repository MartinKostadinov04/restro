# Functionality parts: cross-cutting functions (design, the Log, analytics, roles, purge and backups)

Written 11-10 by the lead session (Opus) for the connector-architecture support session. The question is about capability only: can the POS send or receive this data at all? Whether the data can be trusted is left for a later pass.

The code was read on `origin/or/foundation` at bb8cfa26 (service, Log, events, roles, purge, backup). The designer was read on `origin/st/foundation` at 38dbe70a (D128–D131). "Proposed level" is this session's proposal: the reviewer and Martin decide.

Levels: **DEAL BREAKER**, **SURVIVABLE**, **COVERED**, **NOT POS-RELATED**, as Martin agreed on 11-10. "Inherits" means the row exchanges no data of its own: it only reads what a key function already brought in, so its level is that key function's.

Rough night used for counts: a 50-table club, about 1,000–2,500 Log entries a night (D120). Order and payment counts per night are unknown for the pilot and are marked as rough.

## Notes for the merge

- **Two rows where the decision and the code differ** (outside the capability question, but the reviewer will meet them):
  - X7: D122 says the Log records every line move; the code has no kind for it.
  - X15: Martin's brief says "editable default roles"; the code fixes the defaults and lets a venue copy one.
- **Left out on purpose:** rate limits and backoff (review F6), connection health and the outside watchdog (D120, review F10). They are about whether the POS answers, not whether it can exchange the data, so they belong to the later trust and robustness pass.
- **Not checked:** whether any Log entry today carries a POS user's name. A grep of the Log kinds found none.
