# What a waiter can do in barsy, and what the API offers

Research for ticket #32 (child of the map #29 "Ordering from the menu"). Planning only: no code. Read 2026-10-18 from barsy's official documentation at docs.lukanet.com. Nothing was signed into and no password was typed.

## Answer in short

- **Public help pages (`barsy.help`) describe the waiter's work well enough to name every action**, but several of them say plainly what they do not cover: what prints on the bar ticket, how a declined account is handled, how a row is removed after it reached the bar, how a split is done.
- **Every API method page (`barsy.api`) is behind sign-in.** A signed-out request is redirected to a login form, and the site's `robots.txt` disallows `/barsy.api/` for crawlers. So no parameter, return value or error was read here. What can be said without signing in is only: which methods exist (the docs' own search index lists them), and what the public help pages say each scenario uses.
- **Methods that exist for the waiter's actions** (names only): place and create an account, close it, divide, merge (by place or by client), move, clone, storno, payment link, notes, read one or many accounts, list service statuses, list orders, create a payment, list open accounts per place, create a message.
- **No method exists by name for** declining or approving an account, removing or changing a row on an open account, printing a pre-bill (asking for the bill), or setting a row's status (ordered, ready, served). The one public sentence that bears on rows is that "all open accounts can have items and quantities added and corrected"; the API's way to do that is not readable.
- **Approval is a venue setting, not an API step.** Four modes per cash desk (documented). Whether the API can see the approval is not documented publicly; the account's data carries fields whose names contain `confirmation_output_screen` (name only).
- **Duplicates:** `uuid` is on the create and place pages and on the account input object; the word is absent from the pages that read an account back (`Accounts_get`, `Accounts_getlist`). So finding an account by our id is probably not offered. To confirm signed in.

## Notes behind the table

**Barsy's own web-order scenarios** ([9.3](https://docs.lukanet.com/barsy.help/220-workflows/90-eshop.html), documented): (1) a client request, `Clientorders_create`, reviewed by an operator through several statuses, no stock movement; (2) an open account, `Accounts_create` or `Accounts_place`, reviewed and closed by an operator; (3) an account created and closed automatically, no review ("Невъзможност за предварителна проверка на поръчките"); (4) a stock transfer. Scenario 2 is the shape of "rounds on the table's open bill". The page does not describe declines, prepayment, or what the venue sees.

**Client requests have statuses and a decline; accounts do not, publicly.** A client request keeps configurable statuses (examples: new, confirmed, in progress, ready, fulfilled, declined), moves to "Отказана" when declined, and keeps a full change history ([Клиентска заявка](https://docs.lukanet.com/barsy.help/210-dictionary/client-order.html)). Its API (`Clientorders_create`, `_get`, `_getlist`, `_getstatuslistdata`, `_setstatus`, `_update`, `_getpaymentlink`) exists by name. This is the only place in the public material with a decline state. Whether Restro could use it for table orders is a question for the signed-in reading and for Lukanet; the fiscal research (PR 12, F6) wants the order inside the POS as a sale, which a client request is not ([Клиентска заявка](https://docs.lukanet.com/barsy.help/210-dictionary/client-order.html): "not a completed sale").

**Rights.** Every method page has a "Необходими права" section (index), unreadable here. The help's rights list ([Права](https://docs.lukanet.com/barsy.help/extra/rights.html)) has names only, no descriptions. Ones that match waiter actions: "Нова/редактиране на сметка", "Коригиране на количества в сметка", "Разделяне на сметка", "Сливане на сметки", "Промяна на място", "Сторниране на сметка", "Ново плащане", "Печат на текущата сметка", "Обслужване на поръчки", "Работа с чужда сметка", "Промяна на обслужващ". The API user's rights decide what a call may do, which fits D110: grant only waiter-level rights.

**Where the repo and today's reading agree or differ.** Agree: "For confirmation" and its zone rule; the four approval modes; no popup or sound described for new accounts to approve. New today: barsy sends an automatic staff message on a new account (Съобщения), so "the waiter learns of every order" (D18) may already hold, to be confirmed with Lukanet; the approval setting is per cash-desk line of the bill settings, which means an API caller's own cash desk needs its own approval mode; a partly paid account can lock its rows (after a failed second card payment).

## Limits of this reading

- The public help pages were read through a page-to-text converter that summarises long pages; the quotes above are short and the claims are the ones each page states. A claim the page "does not cover" means the converted text did not contain it.
- The search index lists a word on a page, not its meaning. Statements marked "name only" are about names, never about behaviour.
- The index file lies under `/barsy.api/`, which `robots.txt` disallows for crawlers; it was fetched once, as the earlier fiscal research also cites it, and no API page was crawled.
- Nothing here was tested against any barsy installation.
